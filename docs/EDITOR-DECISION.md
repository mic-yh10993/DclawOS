# 编辑器决策（Phase 3 模块 6）：保留 GtkSourceView，不采纳 Monaco

## 结论

保留当前原生 GtkSourceView 编辑器，不引入 Monaco，不搞双轨。
本模块只做原生渐进改进（见下），不改校验脚本的编辑器门禁
（GtkSourceView 要求 + 禁 WebKit/Vte 导入保持原样，因为结论
就是不引入 web 视图）。

## 决定性理由（评估报告全文见 research/dclawos-reboot/phase3/monaco-evaluation.md）

1. **为编辑器引入第二个浏览器引擎性价比不成立。** 映像里
   Chromium 已承担“浏览器”角色；再为编辑器引入 WebKitGTK
   4.1（仅三主包就约 125MB 安装量，含硬依赖后 140–190MB），
   换回的多光标、智能补全、minimap 并未覆盖用户已确认的
   编辑器工作流（高亮、查找、脏保存、行级 diff、agent 修改
   侧栏、Q7 系统终端均已落地）。用户原则是“优化不减功能”，
   不是“为现代感无限加体积”。
2. **file:// worker 坑正好打在 Monaco 的王牌上。** Monaco 相对
   GtkSourceView 最大的卖点是语言服务，而这部分在 file:// 下
   因 worker 限制失效；绕法（blob 代理、自定义 scheme、回环
   服务器）都需在 WebKitGTK 4.1 下专门实测，且 AMD 路径已
   废弃、ESM 路径要另起打包——“简单方案”走废弃路径，
   “耐久方案”多付整套打包与桥接成本。
3. **双轨是最差折中。** 离线要求下 Monaco 资产必须预装进
   ISO，双轨照付全部体积与安全成本，还要多付两套编辑器
   逻辑、两套 diff 与用户选哪个的困惑。

## 用户纠正后的规则如何适用

2026-10-30 纠正澄清“不要 web”仅指配置不走 web、改本地
GUI 设置，不是指 web 页面不能出现——本决策承认该澄清已
重新打开 Monaco 选项，但经成本核算后仍不采纳：澄清解决
的是“允不允许”的问题，没有解决“值不值”的问题（体积 +
worker 坑仍在）。若未来满足重估触发条件（见下），可重开。

## 本模块做的原生改进（dclawos-editor）

- 查找替换：替换当前/下一个、全部替换（纯文本语义，与
  查找一致；替换含查找词时不死循环）。
- 跳到行：行号输入 + 跳转，越界时报范围。
- 撤销/重做按钮：GtkSource.Buffer 原生能力接出 UI。
- 对比窗口：左右滚动同步（防回环守卫）、等行数 replace
  段落内字符级差异高亮（difflib 行内二次比对）。

## 本模块不做的事（不是功能削减，是未立项）

- 多文件标签页：评估列为“值得做”，但非用户确认的工作流
  必需，且改动 EditorApp 单视图结构；列为后续可选事项。
- 可编辑合并 diff：对比窗口仍只读查看；用户未要求可编辑
  合并，且原生可编辑化方案未经验证够用前不预支成本。
- 智能语言服务、minimap、多光标：Monaco 才有的三项，见上。

## 重估触发条件（满足任一即重开评估，而非现在预支成本）

1. 用户明确把 TypeScript/Python 智能补全、跳转定义列为
   编辑器必备功能（而非“有更好”）。
2. 用户明确要求 diff 必须可编辑合并，且原生渐进方案被验证
   不够用。
3. 未来 DclawOS 引入其他必须用 WebKitGTK 的原生应用，导致
   WebKitGTK 的边际成本不再由编辑器独自承担。

## 政策记录

若未来因上述条件改走 Monaco，必须在评估卡与校验脚本里
显式记录“编辑器是 web 视图的特许例外”，而不是悄悄删门禁
——Phase 2 的门禁是按旧禁令有意写下的，改它本身就是一次
政策变更，需要留痕。
