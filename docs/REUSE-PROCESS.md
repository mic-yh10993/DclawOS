# 复用优先流程（REUSE-PROCESS）

本文件是 DclawOS 的工作合同。任何产品代码提交前，必须按顺序走完以下步骤，不可跳步。

## 第 0 步：检索

写任何代码前，必须对参考库执行检索并贴出命令与结果，例如：

```
grep -rn "<关键词>" vendor/<reference-repo>
grep -rn "function <name>|class <name>|export .<name>" vendor/<reference-repo>
find vendor/<reference-repo> -name "<feature>"
```

输出“候选实现清单”：文件:行号 + 该实现做了什么 + 与需求的差距。

## 第 1 步：复用评估卡

对每个要新增/修改的函数、类、模块，填写：

| 目标符号 | 参考库候选（path:line） | 能否直接复用/适配 | 不能用的具体理由 | 自写 vs 改造成本估计 |
|---|---|---|---|---|
| （填） | （填） | （填） | （填） | （填） |

只有当“不能用的具体理由”成立（依赖冲突、API 不兼容、许可证、版本差异、缺少关键分支）才允许自写。
以下不是合法理由：“我觉得自己写更简单”“参考代码风格不同”“想统一架构”。

## 第 2 步：确认后才写代码

等用户确认评估卡后，才允许写代码。评估卡确认前不写一行产品代码。

## 第 3 步：自写代码的要求

- 通过参考项目对应的测试/示例（先移植这些测试）。
- 在代码注释里写 `// reuse-check: <path:line> 未采用，原因：<理由>`。
- 行为、边界条件、错误处理与参考实现对齐，除非评估卡里明确说明差异。

## 第 4 步：每文件汇报

每完成一个文件，贴出：改了什么、引用了哪些参考位置、测试结果。

## 禁止

- 未检索就新增符号。
- 参考库有等价实现却不说理由。
- 把“参考”当“灵感”。
